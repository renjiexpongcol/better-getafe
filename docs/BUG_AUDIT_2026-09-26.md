# Application bug audit — 2026-09-26

## Summary

The audit confirmed 10 bugs: **0 Critical, 3 High, 5 Medium, and 2 Low**. All 10 have been fixed in the current workspace. The report records each bug as it behaved before the fix and the change made.

The audit traced the major request flows through React state, API handlers, authentication and authorization, database/cache/storage calls, and response handling. It also reviewed configuration, route wiring, Redis-backed state, email jobs, media handling, schema migrations, and selected UI state and validation paths.

## Confirmed bugs

### 1. Process continued after fatal exceptions

- **Bug:** The server could keep accepting requests after an uncaught exception or unhandled promise rejection.
- **Location:** `server/index.js:6-13`.
- **Severity:** High.
- **Cause:** Registered process handlers logged fatal errors but suppressed Node's default exit behavior, leaving potentially inconsistent in-memory and connection state running.
- **Reproduction:** In an isolated server process, trigger an uncaught exception or unhandled rejection, then request a health endpoint. Before the fix, the handler logged the error and the process could remain alive.
- **Expected:** The failed worker exits so its process supervisor can replace it with a clean worker.
- **Actual:** The handlers only logged the error and allowed execution to continue.
- **Fix:** The handlers now log and exit with status 1. This process-crash path was reviewed statically rather than deliberately triggered against the running app.

### 2. Appointment availability missed bookings and concurrent requests could exceed capacity

- **Bug:** Existing appointments could be omitted from slot counts, and simultaneous reservations could both pass the capacity check.
- **Location:** `server/src/services/appointmentScheduling.js:1-22`; `server/src/services/citizenRoutes.js:304-344`.
- **Severity:** High.
- **Cause:** Database timestamp values can arrive as JavaScript `Date` objects while slot lookups use ISO strings, so raw map keys did not match. The booking flow also checked capacity and inserted without serializing requests for the same instant.
- **Reproduction:** Put an appointment at a slot in the database, then request availability for that slot. Before the fix, a `Date`-valued timestamp could be counted under a different key. For the race, submit two bookings for the last open instant concurrently.
- **Expected:** Availability counts all existing bookings and the capacity limit is enforced across app instances.
- **Actual:** A slot could appear open despite bookings, and concurrent requests could both reserve the last capacity.
- **Fix:** Normalize date values to a canonical ISO key, reject non-minute-aligned requests, and acquire a transaction-scoped PostgreSQL advisory lock for the instant before reading capacity and inserting. The lock uses the shared capacity scope. Unit checks cover Date/string normalization and slot alignment; a PostgreSQL transaction check confirmed the lock makes a second transaction wait.

### 3. Staff account welcome email disclosed the initial password

- **Bug:** The new-account email contained the submitted password in both plain text and HTML.
- **Location:** `server/src/services/adminUsersRoutes.js:9-18, 55-63`.
- **Severity:** High.
- **Cause:** The provisioning route interpolated the password directly into an email, creating another persistent copy in mailbox and mail-provider systems.
- **Reproduction:** Create a staff account with a test password and inspect the generated welcome message. Before the fix, the password appeared in both message bodies.
- **Expected:** No password is transmitted by email; the recipient establishes a password through a verified flow.
- **Actual:** The initial password was sent in plaintext email.
- **Fix:** Welcome messages now link to the existing password-reset screen and direct recipients to confirm their email with the existing one-time verification code before choosing a password. The regression test verifies the generated message omits a test password and contains the reset route.

### 4. Staff status changes could overwrite one another

- **Bug:** Two staff updates based on the same prior request status could both commit and create inconsistent status history or notifications.
- **Location:** `server/src/services/staffRoutes.js:150-189`.
- **Severity:** Medium.
- **Cause:** The route read and validated a status, then previously updated the row without checking that the status was still the one it had read.
- **Reproduction:** Submit two valid status changes for the same request concurrently from separate staff sessions.
- **Expected:** One change commits; the competing request receives a conflict and refreshes against the new state.
- **Actual:** Both requests could write based on stale state and append conflicting history.
- **Fix:** The update now compares the stored status and open state in its `WHERE` clause. A missed compare-and-set returns HTTP 409 and rolls back before history or notification inserts.

### 5. Over-limit contact submissions could consume other email addresses' quota

- **Bug:** Requests from an IP already over its limit could still consume rate-limit quota for arbitrary email addresses.
- **Location:** `server/src/services/contactRoutes.js:13-20, 93-105`.
- **Severity:** Medium.
- **Cause:** The route previously evaluated both IP and email buckets before returning the IP-limit response. An over-limit sender could vary the email field on every rejected request.
- **Reproduction:** Exceed the IP limit, then submit additional rejected requests with different email addresses. Before the fix, those addresses' email buckets were also consumed.
- **Expected:** Once the IP bucket rejects a request, no per-email bucket is changed.
- **Actual:** Requests already rejected by the IP limit could rate-limit unrelated recipients.
- **Fix:** The route now returns immediately when the IP limiter rejects; only an IP-allowed request consumes the email bucket. Invalid rate-limit environment values also fail startup validation instead of silently coercing.

### 6. Media upload proxy rejected configured storage prefixes

- **Bug:** Upload URLs using a configured storage prefix other than `media/` were rejected by the development upload proxy.
- **Location:** `server/index.js:1658-1687`; `server/src/services/mediaUploadPath.js:1-12`.
- **Severity:** Medium.
- **Cause:** Upload-key generation used the configured prefix while proxy validation hardcoded `media/`.
- **Reproduction:** Set the storage prefix to a valid custom value, request an upload URL, then upload through the proxy. Before the fix, the generated key failed the proxy's fixed-prefix check.
- **Expected:** The proxy accepts only valid UUID/date/image keys beneath the configured prefix.
- **Actual:** Valid uploads under a custom prefix received HTTP 400.
- **Fix:** Added shared prefix-aware validation and used it in the proxy. Focused tests cover default/custom prefixes and malformed keys.

### 7. Concurrent media completion could return a false failure

- **Bug:** Concurrent completion calls for the same uploaded object could both observe no media row; one would then fail on the unique key even though the other successfully finalized it.
- **Location:** `server/src/repositories/mediaRepository.js:104-166`.
- **Severity:** Medium.
- **Cause:** `SELECT ... FOR UPDATE` does not lock a row that does not yet exist, so it did not serialize first-time inserts.
- **Reproduction:** Send two `/api/media/complete` requests for the same valid pending upload at the same time. Before the fix, the losing insert could surface a uniqueness error to the caller.
- **Expected:** Completion is idempotent for the same owner and storage path; a retry receives the existing media record.
- **Actual:** One completion could report failure after the other had already created the record.
- **Fix:** Use conflict-safe insert with `ON CONFLICT (storage_path) DO NOTHING`, then read and return the existing row after a conflict. A different owner is still rejected. Concurrency behavior was reviewed in code; a live media-row mutation was not performed.

### 8. Redis session registry TTL used milliseconds as seconds

- **Bug:** Session metadata and per-user session indexes could remain in Redis far beyond the signed session's expiration.
- **Location:** `server/index.js:295-307, 347-362`; `server/src/services/sessionRegistry.js:1-12`.
- **Severity:** Medium.
- **Cause:** Token expiry minus `Date.now()` is milliseconds, but Redis `EX` and `EXPIRE` expect seconds. Repeated logins could also shorten the user-session index expiry if a later session had a shorter TTL.
- **Reproduction:** Create a Redis-backed session and inspect the session key TTL. Before the fix, the value was about 1,000 times the intended duration; creating a shorter session could also shorten a shared index.
- **Expected:** Per-session metadata expires with its token and the shared index lasts through the longest remaining session.
- **Actual:** Stale session records accumulated and session listings could contain expired entries.
- **Fix:** Convert remaining milliseconds to ceiling seconds, extend the index TTL only when needed, and prune expired session records when listing sessions. Redis service checks, including TTL conversion and max-expiry behavior, pass.

### 9. News pagination could report a page beyond the available range

- **Bug:** An oversized page number returned an empty slice while metadata still claimed the requested page existed.
- **Location:** `server/index.js:1302-1320` (`GET /api/news`).
- **Severity:** Low.
- **Cause:** The requested positive page was used directly for slicing and response metadata rather than being clamped to the number of pages for the current filter.
- **Reproduction:** Request `/api/news?limit=10&page=999999` when there are fewer than 999,999 pages. Before the fix, the API returned no items and echoed an impossible page number.
- **Expected:** Clamp to the last available page and keep `hasNext`/`hasPrevious` consistent; negative or invalid pages start at page 1.
- **Actual:** Data appeared empty despite matching news existing.
- **Fix:** Compute the page count first and clamp the requested page. API smoke checks verified high and negative page values against the live test server.

### 10. Admin-users middleware returned permission errors before request-format errors

- **Bug:** The admin-users API performed its permission lookup before checking write-origin and JSON content-type rules, producing a permission response for malformed or cross-origin writes and doing avoidable authorization work first.
- **Location:** `server/src/services/adminUsersRoutes.js:26-35`.
- **Severity:** Low.
- **Cause:** The permission middleware ran before the route's origin and content-type guards.
- **Reproduction:** Send a cross-origin write or a non-JSON write to `/api/admin/users` using an authorized test principal. Before the fix, downstream permission behavior could mask the route's 403 or 415 request-validation result.
- **Expected:** Reject cross-origin or unsupported-content writes at the request boundary before querying permission data.
- **Actual:** Permission lookup ran first and could return a different status.
- **Fix:** Origin and content-type checks now run before `requireAccess`. The admin-users route regression suite passes, including 403 and 415 cases.

## Potential issues requiring deployment-specific evidence

- **Welcome-email host fallback:** `server/src/services/adminUsersRoutes.js:60` falls back to `http://localhost:5173` when `general.url` is empty. The application setting maps to `PUBLIC_SITE_URL`, whose deployed value was not verified. If it is unset in production, recipients receive an unusable localhost link. Verify the production setting or derive the link from a trusted configured public host.
- **Email queue recovery with multiple replicas:** `server/src/services/redisInfrastructure.js:86-92` moves all jobs in a shared `email:processing` list back to the pending queue at startup. If one replica starts while another is still sending a job, a duplicate delivery may occur. Confirm whether production runs multiple replicas and test a restart during an in-flight send before changing recovery semantics.
